QUESTIONS & ANSWERS
================================================================================

Q: Will this break anything?
A: No. The fix is additive (adds new behavior) without changing existing code
   paths. Fully backward compatible. Worst case: rollback in 5 minutes.

Q: How much will this slow things down?
A: Imperceptible impact. IV calculations take 2-5 seconds anyway (method
   recalculation). Cache invalidation adds <1ms. Not user-facing slowdown.

Q: Do we need to update the FMP API calls?
A: No. Analyst estimates still fetched once per earnings. IV methods recalculate
   on demand using cached analyst data. No additional FMP calls.

Q: What about other cache tiers (prices, etc.)?
A: Other caches are independent. IV and analyst caches have mutual dependency.
   Only those two need this coordinated invalidation.

Q: How do we know the fix is working?
A: Check logs for "IV method caches invalidated" messages within 1 hour.
   Count iv:method:* Redis keys before/after earnings event.

Q: What if analyst data fetch fails after invalidation?
A: Graceful degradation. IV methods will recalculate with null/empty analyst
   data, returning error response. No crash. Automatic retry next cycle.

Q: Should we do selective method invalidation instead of "all methods"?
A: Not necessary. Cost of invalidating unused methods is negligible.
   Conservative approach (invalidate all) is safer than selective list.

Q: Will this create a thundering herd?
A: No. methodCacheService already has inFlightRequests Map to prevent
   concurrent recalculations of same method.
